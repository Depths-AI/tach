# Tach GPGPU performance showcase

This workspace exercises Tach as a complete browser GPGPU toolchain: a `.tach`
module is compiled into generated TypeScript bindings and WGSL, called through
the public `@depths/tach` API, and executed by hardware WebGPU in Chromium.

The suite has two responsibilities:

1. stress distinct classes of GPU work used by numerical applications,
   simulation, procedural generation, and software rendering; and
2. measure the two visual endpoints of the intended Tach game-engine model:
   every pixel generated procedurally, or every pixel generated by a
   GPGPU triangle-mesh renderer.

The visual endpoints deliberately do not use a graphics or fixed-function
rasterization pipeline. Tach compute kernels produce the final packed RGBA8
pixel buffer. Games may mix the endpoints, but their visual work should fall
between these two algorithmic extremes more often than either endpoint alone.

This is a durable performance harness, not a collection of demo timings. Every
run rebuilds the kernels, type-checks the generated API, performs an untimed
warmup, records raw samples, validates output after timing, and writes a JSON
report plus exact PNG captures of both visual endpoints. A benchmark failure
fails the Playwright run.

## 1. Suite map

| Workload | Primary pressure | Logical work | Physical dispatches |
|---|---|---:|---:|
| Particle prediction | linear storage traffic and simple arithmetic | prediction + commit per repetition | 2 |
| Fixed-depth fractal | dense floating-point iteration and logarithmic color mapping | orbit + color per repetition | 2 |
| Batched 4 × 4 matrices | structured loads and multiply-add arithmetic | product + activation per repetition | 2 |
| Black–Scholes pricing | `log`, `sqrt`, `exp`, polynomial evaluation | price + risk adjustment per repetition | 2 |
| Procedural scene | divergent SDF traversal and per-pixel shading | one complete frame | 2 |
| Triangle-mesh software renderer | transforms, irregular reads, coverage loops, atomics, depth contention | one complete frame | 4 |

The first four workloads are throughput instruments. The last two are
complete-frame visual instruments. Their reported rates therefore answer
different questions and must not be compared as if one `element` represented
the same work everywhere.

## 2. Execution and timing contract

One persistent Tach session owns the adapter, device, pipelines, caches, and
GPU buffers for the whole suite. Workloads execute sequentially in the order
shown above. For each workload the harness:

1. creates deterministic host inputs;
2. creates and uploads persistent GPU buffers;
3. constructs the generated Tach command or commands;
4. submits one untimed warmup and waits for completion;
5. times each sample as:

   ```text
   gpu.submit(commands...) + gpu.idle()
   ```

6. reports the median sample;
7. reads the result back and validates it outside the timed interval; and
8. converts visual readbacks to browser canvases for PNG capture; and
9. destroys every buffer owned by that workload.

The GPU time includes command preparation, compute-pass encoding, bind-group
and dispatch recording, queue submission, and `queue.onSubmittedWorkDone()`.
It excludes:

- Tach compiler execution and generated-code loading;
- Vite compilation and browser startup;
- adapter and device acquisition;
- initial input construction and GPU upload;
- first shader, pipeline, and bind-group creation absorbed by the warmup;
- output readback and correctness checking;
- conversion or transport of the packed pixel buffer to a visible surface;
- input handling, game logic, physics, audio, networking, and other engine
  systems not explicitly represented by a workload.

Consequently, visual `framesPerSecond` is the reciprocal of measured GPGPU
frame production, not a claim about a finished game's presented frame rate.

### Medians and raw samples

`gpuMs` is the median of `gpuSamplesMs`. The large profile takes five samples;
the medium profile takes three. Raw samples are retained because browser
scheduling, power state, shared-memory pressure, thermals, and unrelated
system work can move individual measurements materially even when the median
is stable.

For numerical workloads:

```text
millionElementsPerSecond = elements × repetitions / GPU seconds / 1,000,000
```

`elements` means particle components, fractal pixels, matrix output cells, or
options. For the procedural endpoint it means output pixels; for the mesh
endpoint it means input triangles. Those last two values omit other major work
dimensions such as traversal steps, rasterized fragments, and fixed per-pixel
shading. Use complete-frame milliseconds and FPS when discussing them.

## 3. Dispatch removal, not fusion

Particle, fractal, matrix, and option work consists of two exported indexed
commands. Every invocation accesses only its own one-dimensional element, with
no source loop, atomics, shared memory, or barrier. Tach can therefore move a
command's configured repeat count into an invocation-local loop. Each workload
performs `repetitions × 2` logical stage evaluations with only two physical GPU
dispatches.

The inputs do not evolve between those repetitions. For example, particle
prediction repeatedly evaluates the same initial position and velocity; it is
not a chained multi-timestep physical simulation. This is intentional: these
four cases isolate sustained kernel throughput and repeat-dispatch removal.

The two visual programs do not use artificial repetition. Each timed
submission constructs one meaningful frame. Tach currently emits one physical
kernel per `run`, so the procedural frame uses two dispatches and the mesh
frame uses four. The showcase makes no kernel-fusion claim.

## 4. Workloads

The maintained Tach source is `kernels/benchmarks.tach`; host-side input
construction, references, timing, and reporting live in `src/benchmarks.ts`.

### 4.1 Particle prediction

The first stage performs an Euler-style component update:

```text
predicted[i] = position[i] + velocity[i] × dt
```

The second applies damping and a small bias:

```text
output[i] = predicted[i] × 0.99991 + 0.00003
```

Positions, velocities, the intermediate prediction, and final output are
separate resident `float32` buffers. The workload measures wide, regular
storage traffic plus inexpensive arithmetic. The unit is a component update,
not a three-dimensional body and not a collision-resolved physics step.

### 4.2 Fixed-depth fractal

Each pixel maps to the complex plane and performs exactly 16 composed
quadratic Mandelbrot orbit steps. The first stage writes the squared orbit
magnitude to an intermediate `float32` buffer. The second applies `log2`, maps
the result to a bounded value, and packs an opaque RGBA8 pixel.

Fixed depth removes early-exit variability: every pixel receives the same
orbit-step count even though its numerical trajectory differs. This makes the
workload a dense floating-point and transcendental throughput case rather than
an adaptive fractal renderer.

### 4.3 Batched 4 × 4 matrices

Each first-stage invocation owns one output cell from a row-major 4 × 4
matrix product and reads the four required values from each input matrix. The
second stage applies:

```text
value / (1 + abs(value))
```

Sixteen output-cell invocations constitute one complete product. The
workload represents transform-like structured memory access and arithmetic,
but it intentionally does not claim cache blocking, shared-memory tiling, or a
vendor matrix primitive.

### 4.4 Black–Scholes pricing

One invocation derives deterministic option inputs from its index, evaluates
a single-precision European call-price approximation, and writes the price.
The calculation includes division, `log`, `sqrt`, `exp`, and a polynomial
normal-CDF approximation. A second stage adds a nonlinear risk adjustment.

This is the suite's transcendental-heavy scalar workload. It is useful for
distinguishing raw memory throughput from kernels where substantially more
math is performed per output element.

### 4.5 Procedural scene endpoint

This endpoint begins with no triangle mesh. Tach produces a complete packed
frame from analytic scene definitions.

The trace stage launches one invocation per output pixel. It constructs a
camera ray and advances through a signed-distance field for at most 64 steps
or until it hits a surface or exceeds the scene range. The field combines:

- animated height-varying terrain;
- a moving sphere-like form; and
- a second anisotropically scaled analytic form.

The stage stores the hit position and travel distance in a transient
`float32x4` surface buffer. The shade stage samples the scene again to
reconstruct a normal, evaluates directional lighting and procedural material
bands, applies distance fog and sky color, and packs the final opaque RGBA8
pixel.

The workload exposes the costs that matter to procedural visuals: divergent
traversal length, repeated scene evaluation, vector normalization,
trigonometry, intermediate storage, and full-screen shading. It is not a
single decorative field repeatedly written to the same output.

### 4.6 Triangle-mesh GPGPU endpoint

This endpoint uses indexed triangle data but no graphics pipeline or dedicated
rasterization stage. It is a compute-only software renderer expressed in Tach.

The host creates regularly tessellated, gently displaced mesh layers before
timing. Four Tach stages then produce one frame:

1. **Transform:** animate and project every world-space `float32x4` vertex to
   screen X/Y, normalized depth, and material layer.
2. **Clear:** initialize every atomic visibility pixel to the background
   sentinel.
3. **Rasterize:** give one invocation a triangle, compute its clipped screen
   bounding box, test pixel centers with edge functions, interpolate depth,
   and submit covered fragments through `atomicMin`.
4. **Shade:** load the winning packed owner, recover the triangle, recompute
   barycentric weights, construct its normal, evaluate material and lighting,
   apply depth atmosphere, and pack RGBA8.

Visibility packs a 12-bit quantized depth above a 20-bit triangle identifier.
Unsigned integer ordering therefore makes one atomic minimum select the
nearest triangle, with triangle identity providing deterministic tie-breaking.
The benchmark rejects meshes that exceed the identifier capacity.

Direct per-triangle bounding-box rasterization is appropriate for this
particular scene: triangles are small, regular, coherent, and cover nearly the
whole viewport. A separate tile-binning pass would add setup and indirection
without eliminating much candidate work. This is not a universal assertion
about all meshes. Very large, tiny, sparse, highly overlapping, or irregular
triangles can produce different bottlenecks and may justify a different Tach
program.

Triangle count alone does not describe this workload. Each large mesh layer
spans about 92% of the viewport on each axis and therefore covers roughly 85%
of its pixels. Four such depth-overlapping layers generate approximately
`4 × 0.85 = 3.4` candidate fragments per output pixel when averaged over the
entire frame. Pixels inside the common mesh footprint generally receive four
depth candidates; border pixels receive fewer or none. The atomic visibility
pass selects the nearest candidate. Thus the large case combines 294,912
transformed triangles with substantial overdraw and depth contention across a
2,073,600-pixel visibility buffer.

## 5. Profiles

### 5.1 `gpu-large`: sustained GPU and complete 1080p frames

This profile records five GPU samples and performs no CPU reference work.

| Workload | Exact problem |
|---|---|
| Particles | 16,000,000 components × 16 repetitions |
| Fractal | 3072 × 3072 pixels × 16 orbit steps × 4 repetitions |
| Matrices | 524,288 products × 8 repetitions, or 8,388,608 cells per repetition |
| Options | 4,194,304 options × 4 repetitions |
| Procedural | 1920 × 1080 pixels, up to 64 traversal steps, one frame |
| Mesh | 1920 × 1080 pixels, 294,912 triangles, 4 depth layers, one frame |

Large numerical dimensions target tens of milliseconds rather than
dispatch-dominated toy inputs. Visual dimensions intentionally match this
laptop's 1920 × 1080 display so their milliseconds map directly to a native
frame budget.

### 5.2 `gpu-cpu-medium`: equivalence and accessible comparison

This profile records three GPU samples. The four numerical workloads also run
one untimed CPU warmup and three timed CPU samples.

| Workload | Exact problem |
|---|---|
| Particles | 1,048,576 components × 4 repetitions |
| Fractal | 768 × 768 pixels × 16 orbit steps |
| Matrices | 32,768 products × 2 repetitions, or 524,288 cells per repetition |
| Options | 262,144 options |
| Procedural | 960 × 540 pixels, up to 64 traversal steps, one frame |
| Mesh | 960 × 540 pixels, 57,600 triangles, 2 depth layers, one frame |

The CPU reference is ordinary single-threaded TypeScript over typed arrays on
the browser main thread. It is not native code, SIMD, WebAssembly, workers, or
a tuned library. `gpuVsCpu` means `CPU median / GPU median`; it characterizes
this harness's two implementations and must not be presented as a universal
GPU-versus-CPU ratio.

CPU comparison is intentionally absent from the two visual endpoints. Their
purpose is GPGPU visual-frame throughput, not the irrelevance of reproducing a
compute renderer on the TypeScript main thread.

## 6. Correctness contract

The medium numerical references compare the post-timing GPU readback against
the corresponding TypeScript calculation:

| Workload | Comparison | Maximum accepted difference |
|---|---|---:|
| Particles | each `float32` component | `1e-5` |
| Fractal | each channel of every packed RGBA8 pixel | `32` |
| Matrices | each activated `float32` cell | `1e-5` |
| Options | each adjusted `float32` price | `0.002` |

The fractal reference uses explicit `Math.fround` operations to approximate
the kernel's single-precision evaluation. The byte tolerance still recognizes
that transcendental implementations and chaotic orbit growth can amplify
small backend differences.

Both visual profiles read the completed frame and sample up to 4,096 evenly
spaced pixels. Validation requires opaque alpha and enough variation to reject
an unchanged, empty, or uniform output. This catches missing dispatches,
clears without rendering, broken packing, and many indexing failures. It does
not prove aesthetic quality or pixel equivalence to an independent renderer.

The Playwright contract additionally verifies workload order, sample count,
positive timings, exact dispatch counts, presence or absence of CPU results,
and visual FPS. Readback and every comparison occur after timing.

## 7. Reference execution and observations

These observations came from hardware-accelerated Chromium on 2026-08-13:

```text
GPU: AMD Radeon(TM) Graphics, RDNA-2
CPU: AMD Ryzen 5 5500U, 6 cores / 12 threads
Display: 1920 × 1080
```

They are a concrete record of this machine, browser, driver, power, and
thermal state—not constants embedded in the harness and not release promises.

### 7.1 Large GPU-only execution

| Workload | Raw GPU samples (ms) | Median | Observed rate |
|---|---|---:|---:|
| Particles | 15.6, 13.5, 12.7, 18.7, 15.3 | **15.3 ms** | **16.73 billion component-repetitions/s** |
| Fractal | 15.8, 15.9, 14.9, 12.4, 12.3 | **14.9 ms** | **2.53 billion pixel-repetitions/s** |
| Matrices | 30.8, 31.6, 31.5, 32.4, 32.3 | **31.6 ms** | **132.73 million 4 × 4 products/s** |
| Options | 10.0, 10.1, 8.9, 8.4, 8.6 | **8.9 ms** | **1.89 billion option-repetitions/s** |
| Procedural | 11.9, 8.5, 10.9, 10.6, 9.3 | **10.6 ms** | **94.3 complete frames/s** |
| Mesh | 6.9, 10.3, 9.0, 9.6, 5.3 | **9.0 ms** | **111.1 complete frames/s** |

Observations grounded in this execution:

- The matrix workload was the longest large kernel despite its lower product
  count, which is consistent with sixteen independently dispatched cells,
  structured input reads, intermediate output, and activation per product.
- The transcendental-heavy option workload completed fastest. On this device,
  its arithmetic did not make it slower than the larger storage-heavy cases.
- The procedural endpoint produced a complete 1080p scene within a 90 FPS
  median visual budget, but one 11.9 ms sample exceeded the 11.11 ms deadline.
  The result therefore supports roughly 94 FPS visual throughput, not a claim
  of perfectly paced 90 FPS gameplay.
- Every mesh sample fit inside an 11.11 ms 90 FPS visual budget. The median
  also beat the procedural endpoint by 1.6 ms for the exact scenes measured.
- Neither endpoint met the 8.33 ms 120 FPS budget at its median. Two mesh
  samples did, but that is insufficient evidence for sustained 120 FPS.
- Sample spread is material, especially for the visual endpoints. The median
  is appropriate for throughput comparison; a shipping frame-time contract
  also needs long-run percentiles and presentation measurements.

### 7.2 Medium GPU-versus-CPU execution

The most recent full repository test run produced:

| Workload | GPU median | CPU median | CPU/GPU | Visual FPS |
|---|---:|---:|---:|---:|
| Particles | 4.2 ms | 14.2 ms | **3.38×** | — |
| Fractal | 5.2 ms | 183.9 ms | **35.37×** | — |
| Matrices | 3.9 ms | 24.9 ms | **6.38×** | — |
| Options | 4.6 ms | 50.2 ms | **10.91×** | — |
| Procedural | 5.0 ms | — | — | **200.0 FPS** |
| Mesh | 3.8 ms | — | — | **263.2 FPS** |

All numerical comparisons and both visual validations passed. The visual
scaling is not purely proportional to pixel count: command submission,
per-frame clears, vertex work, scene traversal distribution, and GPU occupancy
remain partly fixed or change with the profile.

### 7.3 What the visual results imply for frame budgets

Using the large medians without pretending that unmeasured engine work is
free:

| Target | Total frame budget | Procedural visual time left | Mesh visual time left |
|---:|---:|---:|---:|
| 30 FPS | 33.33 ms | **22.73 ms** | **24.33 ms** |
| 60 FPS | 16.67 ms | **6.07 ms** | **7.67 ms** |
| 90 FPS | 11.11 ms | **0.51 ms** | **2.11 ms** |
| 120 FPS | 8.33 ms | **−2.27 ms** | **−0.67 ms** |

The remainder is merely arithmetic headroom. It is not measured physics or
presentation capacity. Still, the endpoints establish useful boundaries:

- 1080p/30 leaves substantial room for simulation and other GPGPU systems at
  either visual extreme.
- 1080p/60 fits both measured complete visuals and leaves about 6–8 ms before
  the frame deadline, making it the strongest current full-engine target.
- 1080p/90 is visually attainable for the measured mesh case and marginal for
  the procedural case, but neither leaves a broad whole-engine budget.
- 1080p/120 requires less visual work even before physics and screen transport:
  approximately 21% below the measured procedural median or 7% below the mesh
  median just to cross 8.33 ms.

A mixed game is not guaranteed to be a linear interpolation. Shared work can
reduce cost, while overdraw, synchronization, divergent procedural traversal,
or contention can increase it. The two endpoints are empirical anchors for
designing that mixed workload, not substitutes for benchmarking the eventual
engine frame graph.

## 8. Running the suite

From the repository root, install dependencies, build the native compiler, and
install Chromium once:

```sh
npm ci
npm run compiler
npm run install:browser --workspace=@tach/showcase-ts
```

Run the large GPU profile:

```sh
npm run benchmark:gpu --workspace=@tach/showcase-ts
```

Run the medium comparison profile:

```sh
npm run benchmark:cpu --workspace=@tach/showcase-ts
```

Run both profiles, large first:

```sh
npm run benchmark --workspace=@tach/showcase-ts
```

`npm test --workspace=@tach/showcase-ts` is an alias for the medium profile.
Every command regenerates `build/benchmarks.js` and
`build/benchmarks.d.ts`, type-checks the TypeScript harness, and builds the
Vite application before Playwright opens Chromium.

For interactive inspection:

```sh
npm run dev --workspace=@tach/showcase-ts
```

The page uses `gpu-cpu-medium` by default. Add `?profile=gpu-large` to select
the large profile.

## 9. Reports

Each run overwrites one ignored machine-readable report:

```text
showcase-ts/reports/gpu-large.json
showcase-ts/reports/gpu-cpu-medium.json
showcase-ts/reports/gpu-large-procedural.png
showcase-ts/reports/gpu-large-mesh.png
showcase-ts/reports/gpu-cpu-medium-procedural.png
showcase-ts/reports/gpu-cpu-medium-mesh.png
```

The PNG files are encoded by the browser from the exact post-timing Tach
readbacks. The harness explicitly unpacks each `uint32` as low-byte red, then
green, blue, and alpha, so capture does not depend on host byte order. Canvas
conversion and PNG compression are outside GPU timing. The large captures are
1920 × 1080; medium captures are 960 × 540.

Each report contains:

- UTC generation time and adapter identity;
- profile name;
- stable workload ID and display name;
- formatted problem dimensions;
- sample count, all raw GPU samples, and GPU median;
- CPU median and CPU/GPU ratio when the profile has a reference;
- logical stage evaluations and physical dispatches;
- correctness status and diagnostic text;
- workload-specific million-elements throughput; and
- complete-frame FPS for the two visual endpoints.

The terminal prints workload, GPU median, visual FPS, and CPU median in a
compact table. Preserve the JSON report, machine power state, browser version,
driver version, and thermal conditions when publishing or comparing results.

## 10. Interpreting future changes

Compare raw samples and medians only at identical profile dimensions. A change
that helps arithmetic-heavy options can hurt atomic mesh rasterization; one
aggregate score would conceal that regression. In particular:

- particle performance tracks regular storage and elementary arithmetic;
- fractal and option performance expose different transcendental mixes;
- matrices expose structured repeated reads and intermediate writes;
- procedural performance tracks traversal divergence and scene evaluation;
- mesh performance tracks projected triangle size, overdraw, atomics, and
  visibility contention; and
- complete visual FPS must remain separate from numerical element throughput.

When the engine gains physics, screen presentation, temporal state, or a mixed
procedural/mesh frame, add or extend a benchmark that performs that real work.
Do not infer it from an unrelated kernel or hide it inside a synthetic repeat.
